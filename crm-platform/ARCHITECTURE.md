# GMIdeas CRM — собственная платформа (замена Bitrix24)

Цель: своя self-hosted CRM на собственном сервере (Hetzner), без абонплаты за лицензии,
с полным контролем над данными. Логика и механика — как в Bitrix24, но удобнее под нашу компанию.

## Что заменяем

| Сейчас (Bitrix24) | Будет (наша платформа) |
|---|---|
| Открытые линии | Свой омниканальный inbox (Telegram, Viber, Instagram, Facebook, WhatsApp, Google Business) — **собственные интеграции**, без e-chat |
| Телефония | Свой SIP-шлюз (Asterisk на сервере Hetzner) + запись звонков |
| CRM лиды/сделки/воронки | Своя CRM с канбаном, правами по ролям |
| Складской учёт | Свой модуль: партионный учёт (FIFO), приход/расход/инвентаризация |
| LiqPay / Checkbox / Новая Почта | Переносим рабочие связки как есть (cashflow) |
| Finmap | Свой финмодуль, встроенный в CRM, с ролевым доступом |

> Важно: всё рабочее в Bitrix остаётся в Bitrix. Переносим логику копированием, ничего не ломаем.

### Стек (согласовано)
- **Backend:** Python + **Django** + Django REST Framework, PostgreSQL, Redis (кэш/очереди/realtime), Celery для воркеров интеграций.
- **Realtime (чаты):** Django Channels (WebSocket) поверх Redis.
- **Frontend:** React + TypeScript + Tailwind (дизайн уже прототипирован в `preview.html`).
- **Медиа-хранилище:** MinIO (S3-совместимое, self-hosted) — см. раздел «Оптимизация хранения».
- **Телефония:** Asterisk (уже есть сервер на Hetzner) + ARI/AMI для интеграции, запись разговоров.
- **Деплой:** Docker Compose на сервере Hetzner.

### Очередность (согласовано)
1. **CRM-ядро** (текущий этап): лиды, сделки, воронки, контакты, RBAC + перенос оплат.
2. Омниканальный inbox. 3. Телефония. 4. Склад. 5. Финансы.

### Viber (согласовано — личный номер)
Личный номер «не бот» официального Viber API не имеет. Делаем через **сменный адаптер-коннектор**
(как нынешний e-chat) за интерфейсом `ChannelAdapter`, чтобы ядро не зависело от конкретного провайдера.
⚠️ Риск: сторонний коннектор менее стабилен, возможна блокировка номера со стороны Viber.

### Оптимизация хранения (фото/голос от клиентов)
Это прямой ответ на запрос экономии места:
- **Фото:** на входе пересжимаем в WebP, генерим превью (thumbnail). Оригинал держим в "тёплом", старше N мес — в "холодном" хранилище. Дедупликация по хешу (одинаковые файлы хранятся 1 раз).
- **Голосовые / записи звонков:** перекодируем в **Opus 24–32 kbps** (≈10× меньше WAV, почти без потери разборчивости речи). Опционально — авто-транскрипция в текст (тогда сам аудиофайл можно архивировать).
- **Политики жизненного цикла (lifecycle):** авто-перенос старых медиа в дешёвое хранилище, авто-удаление по retention-правилам.
- **MinIO** позволяет наращивать объём добавлением дисков — сервер расширяется без переезда.

## Права и роли (RBAC)
Динамические роли. Администратор создаёт роль и выдаёт доступ галочками:
- доступ к каждой **открытой линии** отдельно;
- **свои лиды** vs **все лиды** (руководитель отдела видит отдел, менеджер — только своё);
- доступ к каждой **воронке продаж** отдельно;
- доступ к **финансам** — только избранные роли;
- доступ к **складу**, телефонии и т.д.

## Каналы — честные нюансы
- **Telegram** — просто, Bot API, бесплатно.
- **Instagram / Facebook (Messenger, Direct, комментарии)** — через Meta Graph API, нужен бизнес-аккаунт.
- **WhatsApp** — только через WhatsApp Cloud API (Meta берёт плату за диалоги в любом случае).
- **Viber** — личный номер «не бот» официального API не имеет; нужен либо Viber Bot, либо проверенный сторонний коннектор. Это самый сложный канал — обсудим отдельно.
- **Google Business чат (Business Messages)** — возможно, требует верификации Google.

## Открытые вопросы к согласованию
1. Backend на Node/NestJS — ок? (альтернатива — Python/Django).
2. Какой объём диска сейчас на сервере и сколько медиа в месяц (для расчёта хранилища)?
3. Viber: согласны на Viber-бота, или нужен именно личный номер (тогда ищем коннектор)?
4. Порядок этапов — начинаем с CRM-ядра + переноса оплат, или с омниканального inbox?
